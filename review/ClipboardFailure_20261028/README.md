## 已做的候选修改

- Windows 采集与写回入口共用进程内 Mutex；采集 try_lock；写回最多约等待 250ms。
- 文本读取避免外层 OpenClipboard 再嵌套 clipboard-rs::get；改用一次打开和原始读取。
- 文字/HTML/RTF/文件写回复用真实窗口 HWND 的单次打开；每个格式的写入错误向上传播。
- 当来源为 Weixin/WeChat 且真实图片格式已可用时，图片优先于临时文件路径；没有改设置中的全局采集顺序。
- 保留了一个针对剪贴板事务存活的原生回归检查。该检查通过不能替代真实文字粘贴和微信业务验收。

## 重点待审问题（是审查问题，不是已经证明的根因）

1. `watcher.rs` 的时间窗口和最大次数是 OR 退休条件；为何实际会在 144ms 就耗尽 16 次？格式分阶段发布或延迟渲染时是否过早放弃？
2. `read_with_capture` 的 files 优先、首个格式读取失败直接返回，与微信先发布 CF_HDROP、后发布 DIB 的行为有何关系？聊天气泡复制和原图查看器复制必须分开。
3. 整段同步采集持有全局 Mutex，Win32 延迟渲染曾耗时 30 秒；写回只等约 250ms。这是否仍会造成用户可见失败？不得仅凭原生 NULL 句柄实验就认定真实业务根因已闭合。
4. 发布构建的读取失败正文被丢在 DEBUG 级日志里，INFO 日志只剩 read_failed；现有证据是否足以区分格式损坏、剪贴板忙和调用失败？
5. 完整追踪前端 call → paste_clipboard_item → write_to_clipboard → finish_paste → SendInput；用户“粘贴失败”还可能在哪个受证据支持的位置发生？
6. 审查原格式/回环保护、Windows 线程与窗口所有权、错误传播；保留此前 Excel 普通复制与显式图片复制行为。

## 原生机制复现的限度

`native_lock_probe.py` 只读格式元数据、不清空或写入剪贴板。当前运行中，同进程嵌套和跨线程 NULL 句柄打开都成功，内部关闭之后另一调用枚举格式得到 1418；sequence 不变。

这证明了 API 机制，不是 EcoPaste 实际两个线程执行该竞态的调用轨迹，更不是全部现象的唯一根因。不要把机制实验、单个回归检查、构建成功、图片持久化成功和用户业务验收混为一谈。
